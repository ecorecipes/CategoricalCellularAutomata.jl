CategoricalCellularAutomata — Module
CategoricalCellularAutomata

Cellular automata over groups as a cartesian category, generalised cellular automata over group homomorphisms, and wiring-diagram composition: the applied-category-theory layer of the ecorecipes cellular-automata ecosystem.

Cellular automata over a group G form a category with finite products, and cellular automata between different groups (generalised cellular automata over group homomorphisms) form a category with weak products over the free product of the groups (Castillo-Ramirez et al., 2025). The constructions extend from sets to alphabets in any category with finite products, together with a categorical Curtis–Hedlund–Lyndon theorem (Castillo-Ramirez et al., 2026). This package implements those constructions on top of CellularAutomataCore.jl, binds them to Catlab's cartesian-category generics, and produces rules that run on any CellularAutomataCore backend.

Part of the ecorecipes cellular-automata ecosystem.

FiniteGroup(elements, op)

CategoricalCellularAutomata.FullShift — Type
FullShift(A, G)

The full shift A^G: every configuration over the group G with values in the alphabet A. The objects of the category of cellular automata over G.

The product of full shifts (otimes) is strictly associative: (A ⊗ B) ⊗ C and A ⊗ (B ⊗ C) are one full shift, whose configurations hold flat tuples (a, b, c). The unit object munit() holds the single value () and belongs to no particular group: it is a unit for otimes with any full shift.

Cellular automata

CategoricalCellularAutomata.CellularAutomaton — Type
CellularAutomaton(G, S, μ; dom, codom=dom)

The cellular automaton over the group G with memory set S (a vector of distinct elements of G) and local rule μ, from configurations with values in the alphabet dom to configurations with values in codom (alphabets, or FullShifts such as products) (Castillo-Ramirez et al., 2025). It maps a configuration x to the configuration

τ(x)(g) = μ((x(s g))_{s ∈ S}),

that is, μ is called with the tuple of the values of x at s g for the elements s of S, in order. On a torus group s g = s + g, so S lists the offsets of the neighbourhood, the identity being the cell itself. Apply it to a Configuration as τ(x).

Cellular automata over G form a cartesian category whose objects are the FullShifts A^G: they compose (compose(τ, σ) is σ ∘ τ), pair (pair), and have identities, projections, copies and deletions, the Catlab operations of ThCartesianCategory. Two automata are equal (==) when they are equal as maps, which holds exactly when their local rules agree on every pattern over the union of their memory sets.

julia> G = CyclicGroup(8); B = FinAlphabet(0:1);

julia> rule90 = CellularAutomaton(G, [7, 1], p -> xor(p...); dom=B);  # left and right

julia> parent(rule90(Configuration(G, [0, 0, 0, 1, 0, 0, 0, 0])))
8-element Vector{Int64}:
 0
 0
 1
 0
 1
 0
 0
 0

The cartesian category

Cellular automata over a group G form a cartesian category whose objects are full shifts. The package implements Catlab's ThCartesianCategory for FullShift and CellularAutomaton and re-exports its operations:

operationcellular automatonmemory set
compose(τ, σ), σ ∘ τx ↦ σ(τ(x)){s t : s ∈ S, t ∈ T}
id(X)x ↦ x{e}
otimes(X, Y), X ⊗ Ythe product full shift (flat tuples)
pair(σ, τ)x ↦ (σ(x), τ(x))S ∪ T
proj1(X, Y), proj2(X, Y)the projections of X ⊗ Y{e}
otimes(σ, τ)(x, y) ↦ (σ(x), τ(y))S ∪ T
braid(X, Y)(x, y) ↦ (y, x){e}
mcopy(X), delete(X)x ↦ (x, x), x ↦ (){e}
munit()the unit object
dom(τ), codom(τ)the domain and codomain full shifts
CategoricalCellularAutomata.realize — Function
realize(diagram, presentation; generators...)

Evaluate a Catlab wiring diagram, such as one built with @program, in the category of cellular automata: each generator of the presentation named in generators is given a FullShift (an object) or a CellularAutomaton (a morphism), and the diagram's copies, deletions, products and composites become those of cellular automata. Returns one cellular automaton.

pres = @present P(FreeCartesianCategory) begin
    X::Ob
    step::Hom(X, X)
end
d = @program pres (x::X) begin
    y = step(x)
    return (y, step(y))
end
realize(d, pres; X=FullShift(B, G), step=rule90)  # x ↦ (τ(x), τ(τ(x)))

Group homomorphisms and free products

CategoricalCellularAutomata.GroupHom — Type
GroupHom(f, H, G; check=true)

The group homomorphism φ : H → G given by the function f; apply it as φ(h). When H is finite, the homomorphism property φ(a b) = φ(a) φ(b) is checked on every pair of elements unless check=false. φ ∘ ψ composes homomorphisms, and GroupHom(G) is the identity of G.

julia> φ = GroupHom(g -> g % 3, CyclicGroup(6), CyclicGroup(3));

julia> φ(5)
2
source
CategoricalCellularAutomata.FreeProduct — Type
FreeProduct(G1, G2)

The free product G1 ∗ G2 of two finite groups: the infinite group of reduced words, alternating non-identity elements of G1 and G2, multiplied by concatenation and cancellation. A word is a tuple of letters (i, g), with g an element of factor i; the identity is the empty word (). inclusion embeds each factor, induced_hom gives the homomorphism out of the free product determined by one on each factor, and ball lists the words up to a given length.

source

ball(F::FreeProduct, R) -> Vector

The reduced words of the free product F of length at most R, shortest first. Configurations over a free product are infinite; a ball is the part of one that a computation looks at.

source
CategoricalCellularAutomata.inclusion — Function
inclusion(F::FreeProduct, i) -> GroupHom

The inclusion ιᵢ of the i-th factor (1 or 2) into the free product.

CategoricalCellularAutomata.induced_hom — Function
induced_hom(F::FreeProduct, φ1, φ2) -> GroupHom

The unique homomorphism φ : G1 ∗ G2 → K that restricts to φ1 : G1 → K and φ2 : G2 → K on the factors, the universal property of the free product: a word is sent to the product of the images of its letters.

Generalised cellular automata

Cellular automata between configurations over different groups, related by a group homomorphism, and their weak products over free products.

CategoricalCellularAutomata.GeneralizedCA — Type
GeneralizedCA(φ, S, μ; dom, codom=dom)
GeneralizedCA(φ, τ)
GeneralizedCA(τ)

A generalised cellular automaton between groups (Castillo-Ramirez et al., 2025): for a group homomorphism φ : H → G (GroupHom), the map T : A^G → B^H with

T(x)(h) = μ((x(s φ(h)))_{s ∈ S})

for a finite memory set S ⊂ G and local rule μ. It is the pullback φ* after the ordinary cellular automaton τ over G with the same memory set and rule, and the second form builds it from φ and τ; the third treats an ordinary cellular automaton as one over the identity homomorphism. factorize returns (φ, τ). Apply it as T(x) when H is finite, or T(x, h) at one element of any H. Generalised automata compose (compose, ∘), with homomorphism φ ∘ ψ, and are equal (==) when equal as maps.

source
Catlab.Theories.factorize — Method
factorize(T::GeneralizedCA) -> (φ, τ)

The factorisation of a generalised cellular automaton T : A^G → B^H as the pullback along φ : H → G after the ordinary cellular automaton τ : A^G → B^G, so that T == compose(τ, pullback(φ, codom(τ))) (Castillo-Ramirez et al., 2026). (A method of Catlab's factorize.)

source
Catlab.CategoricalAlgebra.Cats.LimitsColimits.Pullbacks.pullback — Method

pullback(φ, A)

The pullback φ* x = x ∘ φ of a configuration over G along a homomorphism φ : H → G: a configuration over H. The second form is the pullback as a generalised cellular automaton A^G → A^H (memory set {e}) for an alphabet or full shift A. (A method of Catlab's pullback.)

CategoricalCellularAutomata.pushforward — Method
pushforward(f, G; dom, codom)

The cellular automaton over G that applies the map of alphabets f : dom → codom to every cell, with memory set {e}: the pushforward f_*, a functor from alphabets to cellular automata over G. It commutes with pullbacks along homomorphisms (Castillo-Ramirez et al., 2026).

Base.:(==) — Method
T1 == T2

Whether two generalised cellular automata are equal as maps. For each element h of the (finite) codomain group, their local rules, read at φ1(h) and φ2(h), are compared on every pattern over the union of the cells they read. Two automata over different homomorphisms can be equal.

CategoricalCellularAutomata.weak_product — Function
weak_product(X1, X2) -> FullShift

The weak product of full shifts A1^G1 and A2^G2 in the category of generalised cellular automata: the full shift (A1 × A2)^(G1 ∗ G2) over the FreeProduct of the groups (Castillo-Ramirez et al., 2025). See weak_projections and weak_pair.

source
CategoricalCellularAutomata.weak_projections — Function
weak_projections(X1, X2) -> (π1, π2)

The projections of the weak_product onto its factors: πᵢ is the generalised cellular automaton over the inclusion ιᵢ : Gᵢ → G1 ∗ G2 that reads the i-th component at the identity.

source
CategoricalCellularAutomata.weak_pair — Function
weak_pair(T1, T2) -> GeneralizedCA

The pairing of generalised cellular automata T1 : X → A1^G1 (over φ1 : G1 → K) and T2 : X → A2^G2 (over φ2 : G2 → K) with a common domain X = B^K: the generalised cellular automaton into the weak_product over the homomorphism induced_hom(G1 ∗ G2, φ1, φ2), whose local rule pairs those of T1 and T2. Composed with the weak_projections it gives back T1 and T2. It is not the only automaton that does: the product is weak because an automaton can be a φ-automaton for several φ (Castillo-Ramirez et al., 2025).

Linear and monotone cellular automata

Cellular automata whose alphabets are vector spaces over a prime field, and partially ordered sets.

CategoricalCellularAutomata.LinearCA — Type
LinearCA(G, coefficients; p)

The linear cellular automaton over the prime field GF(p) on a cyclic or torus group G with the given coefficients s => a_s:

τ(x)(g) = Σ_s a_s x(s g)  (mod p),

on configurations with values in 0:p-1. Linear automata compose and take powers through their coefficients, as elements of the group algebra GF(p)[G] (compose, ∘, ^), which is much faster than composing local rules, and inv inverts one when it is a bijection. CellularAutomaton(L) gives the same automaton as a general one.

julia> rule90 = LinearCA(CyclicGroup(16), [15 => 1, 1 => 1]; p=2);

julia> rule90^4 == LinearCA(CyclicGroup(16), [12 => 1, 4 => 1]; p=2)
true

CategoricalCellularAutomata.is_monotone — Function
is_monotone(τ; leq=(<=), codom_leq=leq) -> Bool

Whether the local rule of the cellular automaton τ is monotone for the order leq on its alphabet (and codom_leq on its codomain's): raising the state of any cell of the memory set never lowers the result. It is checked one cell at a time, which suffices for the product order on patterns. A monotone automaton preserves the cellwise order of configurations, so runs started from ordered initial configurations stay ordered.

Research extension: stochastic cellular automata

Beyond the papers, which treat deterministic automata: stochastic cellular automata as morphisms of a Markov category, where copying is not natural and pairs depend on a coupling.

CategoricalCellularAutomata.StochasticCA — Type
StochasticCA(G, S, κ; dom, codom=dom)
StochasticCA(τ::CellularAutomaton)

A stochastic cellular automaton over the group G. This is a research extension, beyond the categorical framework of the papers, which covers deterministic automata. The local kernel κ maps the tuple of states on the memory set S to a vector of probabilities over the values of the alphabet codom, in order. Each cell's new state is drawn from the kernel of its own pattern, independently of the other cells given the input configuration. The second form is a deterministic cellular automaton, as a kernel of point masses.

Stochastic automata are morphisms of a Markov category, not of a cartesian one: copying the output of a run is not the same as running twice, and two stochastic automata from the same domain pair in many ways, one for each coupling of their random draws (stochastic_pair). distribution computes exact output distributions on small groups. On CellularAutomataCore, LocalRule(T; draw) samples one, and CAProblem(T, u0, tspan; draw) builds a problem from it.

source
CategoricalCellularAutomata.distribution — Function
distribution(T::StochasticCA, x) -> Dict{Configuration,Float64}
distribution(T::StochasticCA, d::AbstractDict) -> Dict{Configuration,Float64}

The exact distribution of the output of a stochastic cellular automaton: for an input configuration x, the product of the cells' kernels; for a distribution d of inputs (configurations to probabilities), the mixture over them, which is how two stochastic automata compose. Outcomes of probability 0 are left out. The number of outcomes is at most |B|^|G|, so this is for small groups; it raises ArgumentError beyond 65536 possible outcomes.

source
CategoricalCellularAutomata.marginal — Function
marginal(d, f) -> Dict

The distribution of f(x) when x has the distribution d, a dictionary of outcomes to probabilities, such as the joint distribution of two cells, marginal(d, y -> (y[0], y[1])).

source
CategoricalCellularAutomata.stochastic_pair — Function
stochastic_pair(T1, T2; coupling=:independent) -> StochasticCA

A stochastic cellular automaton into the product of the codomains of T1 and T2, two stochastic automata with the same domain and group, whose two components have the distributions of T1 and T2. A research extension: in a Markov category such a pair is not unique, and coupling chooses one. With :independent the two components are drawn independently at each cell; with :shared both come from one uniform draw (the comonotone coupling). On CellularAutomataCore these are two layers drawing with different draw numbers, or with the same one.

source
CellularAutomataCore.LocalRule — Method
LocalRule(T::StochasticCA; draw=1)

A CellularAutomataCore rule that samples the stochastic cellular automaton T (over a cyclic or torus group, with equal domain and codomain): each cell's new state is drawn from its kernel by inverting the cumulative probabilities at the counter-based uniform uniform(ctx, draw). Rules that use the same draw on different layers are coupled through it.

Research extension: composing models

CellularAutomataCore models composed along undirected wiring diagrams over shared layers.

CategoricalCellularAutomata.OpenCAModel — Type
OpenCAModel(model; ports=all states, reads=())

A CellularAutomataCore CAModel with some of its state layers exposed as ports, in order, for composition with an undirected wiring diagram (oapply). Layers listed in reads are read but not updated by this model: in a composite, its rule's result for them is ignored, and another box may own them.

source
Catlab.WiringDiagrams.WiringDiagramAlgebras.oapply — Method
oapply(diagram, boxes; dims=2, space=nothing, name=:composite, shared_randomness=false) -> CAModel

Compose CellularAutomataCore models along an undirected wiring diagram, such as one written with Catlab's @relation. boxes gives an OpenCAModel for each box of the diagram, as a vector in the diagram's order or a NamedTuple by box name. A research extension, beyond the papers. (A method of Catlab's oapply.)

The ports of each box are matched, in order, to the junctions its ports attach to, and every junction becomes one state layer of the composite, named after the junction's variable. Layers a box does not expose become layers of their own, named box_layer. Each layer is updated by the one box that owns it: the box that exposes it without listing it in reads. Two owners raise LayerConflictError; a layer without one keeps its state. All boxes update synchronously from the same state, so the composite is the pairing of the boxes' updates, and its neighbourhood is the union of theirs.

The composite's parameters are the boxes' default parameters, one NamedTuple per box, named after the box. Its kernel fields and covariates are the union of the boxes'. Each box draws its own random numbers, from a seed derived from its name, unless shared_randomness=true, in which case boxes that use the same draw numbers see the same uniforms. Every box's rule must name its neighbourhood (Moore, VonNeumann, Hexagonal, Offsets, ...), which is resolved on space, a CellularAutomataCore space of the kind the composite will run on (a hexagonal grid for Hexagonal neighbourhoods; only its shape matters, not its size), or, if space is nothing, on a square lattice of dims dimensions. On a GraphSpace every box must read GraphNeighbours(), and the composite does too. The composite must have at least two layers.

Research extension: maps between models

Maps of cell states that commute with the rules of two CellularAutomataCore models: they send every run of one model to a run of the other, and with the models they form a category.

CategoricalCellularAutomata.ModelMap — Type
ModelMap(dom, codom, h; parameters=nothing, section=nothing)

A map from the CellularAutomataCore CAModel dom to the model codom: h sends a cell state of dom (a value, or a NamedTuple with one field per state variable if dom has several) to a cell state of codom, and parameters sends the parameters of a problem of dom to those of codom (by default, each parameter of codom takes the value of the parameter of the same name, or its default). section, if given, lifts a cell state of codom to one of dom (h(section(b)) == b), which a callback needs in order to move with the map (see pushforward). A research extension, beyond the papers.

It is a map of models when it commutes with the rules: for every cell, its neighbours and its CellularAutomataCore.CellContext, the next state of dom mapped by h is the next state of codom from the mapped cell and neighbours, with the mapped parameters and the same cell id, time and seed, so the same random numbers (is_model_map). Then every run of dom mapped by h is the run of codom from the mapped initial state (pushforward), exactly, for deterministic and stochastic models. Such maps forget what does not feed back on the rest: a label carried along (which introduction a case descends from, the colours of the immigration game), or a layer that only records.

Models and the maps between them form a category (compose).

source
CategoricalCellularAutomata.is_model_map — Function
is_model_map(f::ModelMap; cells=nothing, p=nothing, contexts=8, samples=nothing,
             space=nothing, dims=2) -> Bool
is_model_map(f::ModelMap, prob::CAProblem; alg=Synchronous(), callback, kwargs...) -> Bool

Whether f commutes with the rules of its domain and codomain: for every cell state and every list of neighbour states drawn from cells (by default every combination of the values in the domains of f.dom's state variables), and for contexts cell contexts (cell ids, times and seeds 1:contexts, with the domain's parameters p, by default its defaults, and the codomain's f.parameters(p)), the domain's next state mapped by f equals the codomain's next state from the mapped cell and neighbours. This is a check of every local configuration, so for a deterministic rule that does not read the cell context a true proves that f is a map of models; for a stochastic rule it checks the random numbers on those contexts.

The number of neighbours comes from the domain's neighbourhood on a square lattice of dims dimensions, or on space (a GraphSpace for a model that reads a graph: every degree that occurs is checked). For a block rule the local configurations are the blocks, and the new blocks are compared. The number of local configurations checked must stay below PATTERN_LIMIT, or ArgumentError is raised; with samples set, that many configurations are drawn at random from cells for each context instead, which can find a failure but proves nothing.

This form sees only the rules, not what a problem adds to them. The second form checks one problem by running it: it solves prob and pushforward(f, prob; callback) with the scheme alg (and kwargs, such as saveat), and compares every saved state, exactly. It is the check for models that read covariates or kernel fields, which the first form refuses, and for callbacks; a block rule needs alg=Margolus(). callback is as for pushforward, so callback=:lift checks a quotient with the original's callback and callback=:lift_step one that treats the rule and the callback as one step. A false disproves the map; a true holds for that problem and span only, since a run may not reach what would tell them apart.

source
CategoricalCellularAutomata.pushforward — Method
pushforward(f::ModelMap, u)
pushforward(f::ModelMap, prob::CAProblem; callback, alg) -> CAProblem

The state u of a problem of f's domain mapped by f, cell by cell: a state of its codomain. The second form maps a problem of the domain (built from it with CAProblem(model, ...), possibly pulled back along maps of spaces since) to the problem of the codomain on the same space, from the mapped initial state, with the mapped parameters and the same seed, time span, covariates, mask and solver keywords. When f is a map of models (is_model_map), the solution of the new problem is the original solution mapped by f, state by state.

A callback stored with prob acts on the domain's whole state, and belongs to the domain: a problem with one raises ArgumentError unless callback says what the new problem has: its own callback, nothing for none, or :lift. With :lift the original callback runs on the codomain, for a map with a section and identity parameters (every quotient has both): after each step the state is lifted, the callback acts on the lifted state, and the result is mapped down. It sees integ.u, t, p, alg, backend and retcode, and integ.prob is the original problem, whose seed the new one shares; it may reassign integ.p and call terminate!, u_modified! and add_tstop!. What h forgets is filled back in by the section each time, so a callback that depends on it, or keeps something there for later, changes the run. A map of models says nothing about callbacks, so check the pair by running both with is_model_map.

:lift maps down between the rule and the callback, so a layer that the rule writes and the callback reads in the same step is gone before it is read. callback=:lift_step treats the rule and the callback as one step, under the same conditions on f: the state is lifted, the original problem takes a whole step with the scheme alg (by default Synchronous(), and the only use of alg), and the result is mapped down. So f may forget what lives only inside a step, and when :lift gives a map the two give the same run. The new problem is solved with solve(new), on the default backend and scheme whatever the original uses, since its rule and callback are the original's whole step and run on the original's own backend. Callbacks given to it act between whole steps.

A problem whose rule is not the domain's raises DomainMismatchError; a mapped initial state outside a state variable's domain raises CellularAutomataCore.InvalidStateError, and a missing covariate of the codomain an ArgumentError.

CategoricalCellularAutomata.quotient — Function
quotient(model, h, section; states, name, description="") -> ModelMap

The map from model to its quotient by the map of cell states h, a new model that needs no rule of its own: section lifts a cell state of the quotient to one of model (h(section(b)) == b), and the quotient's rule lifts a cell and its neighbours, applies model's rule and maps the result down with h. It has states (as for CAModel) and model's parameters, covariates and kernel fields, whose sources read the lifted cell states.

The new model is defined for any h, but the result is a map of models only if the dynamics do not depend on the lift: is_model_map is the real test of that, and fails when what h forgets feeds back. When it is one, this is the only rule that h commutes with, whichever section is used, and every map of models that does not distinguish what h forgets factors through it. A problem with a callback moves with callback=:lift, or callback=:lift_step to treat the rule and the callback as one step (pushforward). A block rule's quotient is a block rule, lifting the block and mapping the new block down. Event rules, whose rule gives rates rather than a next state, raise ArgumentError.

source
CategoricalCellularAutomata.forget_layers — Function
forget_layers(model, layers...; name) -> ModelMap

The quotient of model that forgets some of its state layers: the cell states keep the other layers, and a cell is lifted by giving the forgotten layers their defaults. It is a map of models when the forgotten layers do not feed back on the ones kept (is_model_map): layers that only record, such as the time at which a cell was reached, or labels the rule never reads. Naming a layer the model does not have, or every layer, raises ArgumentError.

AlgebraicInterfaces.compose — Method
compose(f::ModelMap, g::ModelMap) -> ModelMap
id(m::CAModel) -> ModelMap

CellularAutomataCore models and the maps between them form a category, an instance of Catlab's ThCategory: compose(f, g) is f followed by g (cell states and parameters go through both maps, and sections in reverse), raising DomainMismatchError unless the codomain of f is the domain of g (the same model object); id(m) is the identity of m. Composites of maps of models are maps of models, and pushing a problem forward along compose(f, g) is pushing it along f, then g.

Pulling back along a map of spaces (pullback) is a functor on this category: pushing a pulled-back problem forward along a map of models gives the pullback of the pushed-forward problem, with the same solutions.

The Curtis–Hedlund–Lyndon theorem

CategoricalCellularAutomata.is_equivariant — Function
is_equivariant(f, G, A; rng=nothing, samples=200) -> Bool

Whether the map f of configurations over the group G with values in the alphabet A commutes with the shifts: f(g·x) == g·f(x) for every element g and configuration x (see shift). Every configuration is tried when there are at most 65536 of them; otherwise samples random configurations drawn with the random number generator rng, which must then be given. Over a finite group, an equivariant map is a cellular automaton (cellular_automaton).

source
CategoricalCellularAutomata.cellular_automaton — Function
cellular_automaton(f, G; dom, codom=dom) -> CellularAutomaton

The cellular automaton that agrees with the map f of configurations over the finite group G, if f is one: its memory set is the whole of G and its local rule reads f at the identity cell. By the Curtis–Hedlund–Lyndon theorem (Castillo-Ramirez et al., 2026) the result equals f exactly when f commutes with the shifts (is_equivariant). minimal_neighbourhood then reduces the memory set to the cells the rule depends on.

CategoricalCellularAutomata.minimal_neighbourhood — Function
minimal_neighbourhood(τ) -> CellularAutomaton

The same cellular automaton with the smallest memory set: the elements of the memory set on which the local rule actually depends, found by trying every pattern. The result equals τ (==). Raises ArgumentError when there are more than about four million patterns to try.

CategoricalCellularAutomata.CellularAutomaton — Method

The cellular automaton over torus_group(space) given by a CellularAutomataCore rule (Life(), Wolfram(30), a LocalRule, ...) on a periodic lattice: its memory set is the identity (the cell itself) followed by the rule's neighbourhood, and its local rule calls the core rule with parameters p.
